## 1. Цель работы

Изучить современные возможности PostgreSQL: тип `JSONB` для слабоструктурированных атрибутов, индексирование JSONB с помощью GIN, анализ планов выполнения `EXPLAIN`/`EXPLAIN ANALYZE`, B-tree- и составные индексы, а также оценить влияние индексов на скорость чтения и массовой вставки.

**Требования задания:**

3. Выбрать 2–3 «тяжёлых» запроса и снять планы `EXPLAIN ANALYZE`.
4. Добавить B-tree-индексы, повторно снять планы и объяснить изменения.
5. Создать GIN-индекс по JSONB и показать его использование.
6. Сравнить массовую вставку в таблицу с индексом и без индекса.
7. Обосновать выбор индексов по планам.

## 2. Теоретическая база

### 2.1. JSON и JSONB

PostgreSQL поддерживает два типа для JSON:

| Тип | Особенности |
|---|---|
| `JSON` | хранит текст как есть; сохраняет пробелы и порядок ключей; не индексируется GIN |
| `JSONB` | хранит разобранное двоичное представление; удаляет незначащие пробелы и дубликаты ключей; поддерживает индексирование и быстрый доступ |

`JSONB` применяют для слабоструктурированных или изменчивых атрибутов, набор которых неудобно описывать фиксированными столбцами: характеристики смартфона, книги, одежды. Для устойчивых и часто используемых полей лучше обычные столбцы и связи — иначе теряются преимущества реляционной модели и контроль целостности.

### 2.2. Операторы JSONB

| Оператор | Что возвращает |
|---|---|
| `->` | значение по ключу или индексу как `JSON` |
| `->>` | значение по ключу как `TEXT` |
| `#>` | значение по пути как `JSON` |
| `#>>` | значение по пути как `TEXT` |
| `@>` | `TRUE`, если документ содержит указанный фрагмент |
| `?` | `TRUE`, если ключ существует |
| `?|`, `?&` | проверка наличия любого / всех ключей |

Пример:

```sql
SELECT attributes ->> 'color' AS color
FROM products
WHERE attributes @> '{"color":"black"}';
```

### 2.3. Индексы и планы

**Индекс** — вспомогательная структура для быстрого поиска строк без полного просмотра таблицы.

| Тип доступа | Когда используется |
|---|---|
| `Seq Scan` | читает всю таблицу; эффективен при выборке большой доли строк |
| `Index Scan` | находит строки через индекс; эффективен при малой выборке |
| `Index Only Scan` | данные берутся из индекса без обращения к таблице |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | промежуточный вариант для умеренно избирательных условий |

B-tree — основной тип индекса; эффективен для равенства, диапазонов (`>`, `<`, `BETWEEN`) и сортировки. Составной индекс `(category_id, price)` применим для условий по первому столбцу или префиксу. GIN (Generalized Inverted Index) применяется для JSONB, массивов и полнотекстового поиска; он поддерживает оператор `@>`.

`EXPLAIN` показывает план и оценку стоимости, не выполняя запрос. `EXPLAIN ANALYZE` реально выполняет запрос и показывает фактическое время и число строк. Модификатор `BUFFERS` добавляет обращения к страницам.

## 4. JSONB-атрибуты товаров

```sql
ALTER TABLE products
    ADD COLUMN IF NOT EXISTS attributes JSONB;

ALTER TABLE products
    ADD CONSTRAINT chk_products_attributes_object
    CHECK (attributes IS NULL OR jsonb_typeof(attributes) = 'object');
```

Характеристики заполняются в зависимости от категории:

| Категория | Пример атрибутов |
|---|---|
| Смартфоны | `{"color":"black","screen_in":6.5,"memory_gb":128,"5g":true}` |
| Ноутбуки | `{"cpu":"Intel Core i5","ram_gb":16,"storage_gb":512,"screen_in":15.6}` |
| Аудиотехника | `{"color":"black","wireless":true,"battery_h":30}` |
| Кухонная техника | `{"power_w":1500,"color":"silver","warranty_years":2}` |
| Пылесосы | `{"power_w":2000,"bagless":true,"color":"red"}` |
| Мужская одежда | `{"size":"L","color":"blue","material":"cotton"}` |
| Женская одежда | `{"size":"M","color":"black","material":"polyester"}` |
| Книги | `{"author":"Иванов И.И.","pages":320,"cover":"hard"}` |
| Спорт и отдых | `{"kind":"fitness","weight_kg":5,"color":"black"}` |

Дополнительно каждому товару добавлен уникальный артикул:

```sql
UPDATE products
SET attributes = jsonb_set(
        attributes,
        '{sku}',
        to_jsonb('SKU-' || lpad(id::text, 4, '0'))
    );
```

В результате атрибуты заполнены у всех 1200 товаров, а `sku` позволяет показать точечный поиск по GIN-индексу.

## 5. Запросы к JSONB

### 5.1. Извлечение полей `->` и `->>`

```sql
SELECT id,
       title,
       attributes -> 'screen_in'  AS screen_json,
       attributes ->> 'screen_in' AS screen_text,
       attributes ->> 'color'     AS color
FROM products
WHERE category_id = 2
ORDER BY id
LIMIT 10;
```

**Результат (фрагмент):**

| id | title | screen_json | screen_text | color |
|---:|---|---:|---:|---|
| 1 | Смартфон №1 | 6.5 | 6.5 | black |
| 10 | Смартфон №10 | 6.5 | 6.5 | black |
| 19 | Смартфон №19 | 6.5 | 6.5 | black |
| 28 | Смартфон №28 | 6.5 | 6.5 | black |
| 37 | Смартфон №37 | 6.5 | 6.5 | black |

`->` вернул JSON-значение `6.5`, `->>` — текст `6.5`. Для арифметики или сравнения текст нужно приводить к числу.

### 5.2. Проверка наличия ключа `?` и пути `#>>`

```sql
SELECT id,
       title,
       attributes ->> 'author' AS author,
       (attributes ->> 'pages')::int AS pages
FROM products
WHERE category_id = 11
  AND attributes ? 'author'
ORDER BY pages DESC
LIMIT 10;
```

**Результат (фрагмент):**

| id | title | author | pages |
|---:|---|---|---:|
| 476 | Книга №476 | Иванов И.И. | 320 |
| 8 | Книга №8 | Иванов И.И. | 320 |
| 980 | Книга №980 | Иванов И.И. | 320 |
| 917 | Книга №917 | Иванов И.И. | 320 |
| 26 | Книга №26 | Иванов И.И. | 320 |

```sql
SELECT id,
       title,
       attributes #>> '{cpu}' AS cpu,
       attributes #>> '{ram_gb}' AS ram_gb
FROM products
WHERE attributes @> '{"cpu":"Intel Core i5"}'::jsonb
ORDER BY id
LIMIT 10;
```

**Результат (фрагмент):**

| id | title | cpu | ram_gb |
|---:|---|---|---:|
| 2 | Ноутбук №2 | Intel Core i5 | 16 |
| 11 | Ноутбук №11 | Intel Core i5 | 16 |
| 20 | Ноутбук №20 | Intel Core i5 | 16 |

### 5.3. Проверка вхождения `@>`

SELECT id, title, attributes

**Результат (фрагмент):**

## 6. Планы выполнения до и после индексов

Перед снятием планов выполнены `VACUUM (ANALYZE)` и удалены новые индексы, чтобы получить честное состояние «до». После создания индексов снова выполнен `ANALYZE`.

### 6.1. Запрос по товарам: категория + цена

```sql
SELECT id, title, price
FROM products
WHERE category_id = 2
  AND price < 3000
ORDER BY price
LIMIT 20;
```

**До индекса:**

```text
Bitmap Heap Scan on products
  Recheck Cond: (category_id = 2)
  Filter: (price < 3000)
  Rows Removed by Filter: 103
  ->  Bitmap Index Scan on idx_products_category
        Index Cond: (category_id = 2)
Execution Time: 0.122 ms
```

**После индекса `(category_id, price)`:**

```text
Index Scan using idx_products_category_price on products
  Index Cond: ((category_id = 2) AND (price < 3000))
Execution Time: 0.111 ms
```

**Вывод:** план изменился с `Bitmap Heap Scan` + отдельная проверка `price` на `Index Scan` по составному индексу. Индекс сразу содержит оба условия, поэтому не нужно читать и отфильтровывать лишние строки категории. На 1200 строках разница по времени мала (0.122 → 0.111 мс), но структура плана и число буферов улучшились.

### 6.2. Запрос по заказам: статус + диапазон дат

```sql
SELECT id, user_id, total_amount, created_at
FROM orders
WHERE status = 'paid'
  AND created_at >= '2026-01-01'
  AND created_at < '2026-04-01'
ORDER BY created_at;
```

**До индекса:**

```text
Seq Scan on orders
  Filter: ((created_at >= ...) AND (created_at < ...) AND (status = 'paid'))
  Rows Removed by Filter: 1464
Execution Time: 0.112 ms
```

**После индекса `(status, created_at)`:**

```text
Bitmap Heap Scan on orders
  Recheck Cond: ((status = 'paid') AND (created_at >= ...) AND (created_at < ...))
  Heap Blocks: exact=3
  ->  Bitmap Index Scan on idx_orders_status_created
        Index Cond: ((status = 'paid') AND (created_at >= ...) AND (created_at < ...))
Execution Time: 0.094 ms
```

**Вывод:** последовательное сканирование 1500 строк заменилось индексным доступом. Составной индекс соответствует порядку условий: сначала равенство по `status`, затем диапазон по `created_at`; это классический шаблон для B-tree.

### 6.3. Запрос по JSONB: точный артикул

```sql
SELECT id, title
FROM products
WHERE attributes @> '{"sku":"SKU-0854"}'::jsonb;
```

**До GIN-индекса:**

```text
Seq Scan on products
  Filter: (attributes @> '{"sku": "SKU-0854"}'::jsonb)
  Rows Removed by Filter: 1199
  Buffers: shared hit=145
Execution Time: 0.330 ms
```

**После GIN-индекса:**

```text
Bitmap Heap Scan on products
  Recheck Cond: (attributes @> '{"sku": "SKU-0854"}'::jsonb)
  Heap Blocks: exact=1
  ->  Bitmap Index Scan on idx_products_attributes_gin
        Index Cond: (attributes @> '{"sku": "SKU-0854"}'::jsonb)
Execution Time: 0.042 ms
```

**Вывод:** GIN-индекс позволил перейти от полного перебора 1200 строк к точечному поиску: время сократилось примерно в 8 раз, число буферов — с 145 до 6.

## 7. GIN-индекс для JSONB

```sql
CREATE INDEX idx_products_attributes_gin
    ON products USING GIN (attributes);
```

GIN строит инвертированный индекс: для каждого ключа и значения хранит список строк, где они встречаются. Поэтому оператор `@>` («содержит фрагмент») может использовать индекс, а обычный B-tree для этого не подходит.

Проверка:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title
FROM products
WHERE attributes @> '{"sku":"SKU-0854"}'::jsonb;
```

План содержит `Bitmap Index Scan on idx_products_attributes_gin` — индекс действительно используется.

> Для неуникальных и часто встречающихся значений (например, `"color":"black"` — 534 строки) планировщик может предпочесть `Seq Scan`, потому что на маленькой таблице полный перебор дешевле. GIN особенно выигрывает на больших таблицах и избирательных запросах.

## 8. Цена индексов: массовая вставка

Созданы две временные таблицы с одинаковой структурой. У второй — индекс `(category_id, price)`. В каждую вставлено по 100 000 строк.

```sql
CREATE TEMP TABLE lab6_insert_no_index (...);
CREATE TEMP TABLE lab6_insert_with_index (...);
CREATE INDEX lab6_insert_with_index_idx
    ON lab6_insert_with_index(category_id, price);

EXPLAIN (ANALYZE, BUFFERS, TIMING)
INSERT INTO lab6_insert_no_index
SELECT g, g % 9 + 2, (g % 9000) + 100, 'payload-' || g
FROM generate_series(1, 100000) AS g;

EXPLAIN (ANALYZE, BUFFERS, TIMING)
INSERT INTO lab6_insert_with_index
SELECT g, g % 9 + 2, (g % 9000) + 100, 'payload-' || g
FROM generate_series(1, 100000) AS g;
```

**Результат:**

| Таблица | Время вставки 100 000 строк |
|---|---:|
| Без индекса | 55.790 мс |
| С индексом `(category_id, price)` | 229.649 мс |

Индекс замедлил вставку примерно в **4,1 раза**: на каждую строку нужно обновить B-tree. Это наглядно показывает цену индексов — они ускоряют чтение, но замедляют `INSERT`/`UPDATE`/`DELETE` и занимают диск. Поэтому индексы создают осознанно, под конкретные частые запросы, а не на все столбцы подряд.

## 9. Обоснование выбранных индексов

| Индекс | Запрос | Почему выбран |
|---|---|---|
| `idx_products_category_price (category_id, price)` | товары категории с фильтром по цене | составной B-tree покрывает равенство и диапазон; заменяет Bitmap + фильтр на Index Scan |
| `idx_orders_status_created (status, created_at)` | заказы по статусу и периоду | равенство по первому столбцу, диапазон по второму — оптимальный порядок для B-tree |
| `idx_products_attributes_gin (attributes)` | `attributes @> '{...}'` | GIN поддерживает containment для JSONB; B-tree для этого неэффективен |
| `idx_products_seller`, `idx_products_category`, `idx_orders_user`, `idx_reviews_product` и др. | соединения и фильтры из ЛР №2–4 | уже созданы по внешним ключам; поддерживают JOIN и проверки ссылочной целостности |

Индекс по `products.title` не создавался: поиск по названию в отчётах не является массовым, а индекс замедлял бы вставку. Индекс по `orders.created_at` отдельно не нужен, так как его покрывает составной `(status, created_at)` для типового фильтра по статусу и дате.

## 11. Ответы на контрольные вопросы

### 1. Что такое тип JSONB, чем он отличается от JSON и для каких данных подходит?

`JSON` хранит текст как есть, `JSONB` — разобранное двоичное представление, которое поддерживает индексирование, быстрее ищет по ключам, удаляет незначащие пробелы и дубликаты ключей. `JSONB` подходит для слабоструктурированных и изменчивых атрибутов: характеристик товаров, метаданных, событий.

### 2. Какими операторами извлекают поля из JSONB и проверяют вхождение фрагмента?

`->` извлекает значение по ключу как JSON, `->>` — как текст, `#>` и `#>>` — по пути. `@>` проверяет, содержит ли документ указанный фрагмент; `?` — наличие ключа; `?|` и `?&` — наличие любого/всех ключей.

### 3. Что такое индекс и как он ускоряет выборку данных?

Индекс — вспомогательная структура (обычно дерево), которая позволяет найти нужные строки, не просматривая всю таблицу. Для условия `WHERE` планировщик может использовать индексный доступ вместо последовательного сканирования.

### 4. Чем последовательное сканирование (Seq Scan) отличается от индексного (Index Scan)?

`Seq Scan` читает все блоки таблицы подряд и подходит при выборке большой доли строк. `Index Scan` находит строки через индекс и читает только нужные блоки; эффективен при малой, избирательной выборке. `Index Only Scan` может вообще не обращаться к таблице, если все нужные столбцы есть в индексе.

### 5. Какой тип индекса используется по умолчанию и для каких условий он эффективен?

По умолчанию используется B-tree. Он эффективен для равенства, диапазонов (`>`, `<`, `BETWEEN`), сортировки и префиксных условий составного индекса.

### 6. Что показывает команда EXPLAIN и чем от неё отличается EXPLAIN ANALYZE?

`EXPLAIN` показывает выбранный план и оценку стоимости, не выполняя запрос. `EXPLAIN ANALYZE` реально выполняет запрос и добавляет фактическое время, число строк и циклов. `BUFFERS` добавляет статистику обращений к страницам.

### 7. Как по плану выполнения определить, используется ли индекс?

Нужно искать узлы `Index Scan`, `Index Only Scan`, `Bitmap Index Scan` с именем индекса. Например, `Index Scan using idx_products_category_price` означает, что индекс задействован. `Seq Scan` означает полный перебор таблицы.

### 8. Почему индексы не следует создавать на все столбцы подряд? Какова их цена?

Индексы занимают диск и замедляют вставку, обновление и удаление, потому что их нужно поддерживать в актуальном состоянии. Кроме того, планировщик может не использовать индекс, если выборка недостаточно избирательна. Индексы создают под конкретные частые запросы.

### 9. Что такое GIN-индекс и в каких случаях он применяется?

GIN (Generalized Inverted Index) — обобщённый инвертированный индекс. Он применяется для JSONB, массивов и полнотекстового поиска, когда нужно проверять вхождение элементов или фрагментов (`@>`, `?`, `@@`). Для обычных скалярных сравнений он не нужен.

### 10. Как индексы влияют на операции вставки и обновления данных?

Каждая вставка или обновление индексируемого столбца требует обновить все связанные индексы. Чем больше индексов, тем медленнее запись и больше журнальных операций. В работе вставка 100 000 строк с одним B-tree-индексом заняла 229.649 мс против 55.790 мс без индекса.
