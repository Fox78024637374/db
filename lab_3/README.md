## 2. Теоретическая база

### 2.1. Соединение таблиц (`JOIN`)

В нормализованной базе данные распределены по таблицам, поэтому для осмысленного результата их соединяют. Соединение объединяет строки двух таблиц по условию из секции `ON` — обычно по равенству внешнего ключа одной таблицы и первичного ключа другой.

```sql
SELECT p.title, c.name AS category, s.store_name AS seller
FROM products AS p
JOIN categories AS c ON c.id = p.category_id
JOIN sellers    AS s ON s.id = p.seller_id;
```

| Вид соединения | Что возвращает |
|---|---|
| `INNER JOIN` | только пары строк, для которых условие истинно |
| `LEFT JOIN` | все строки левой таблицы; если пары нет — `NULL` справа |
| `RIGHT JOIN` | все строки правой таблицы; если пары нет — `NULL` слева |
| `FULL JOIN` | строки обеих таблиц, включая несовпавшие |
| `CROSS JOIN` | декартово произведение всех строк |
| `SELF JOIN` | соединение таблицы с самой собой (например, иерархия категорий) |

`LEFT JOIN` незаменим, когда нужно показать **отсутствие** связи: товары без отзывов, продавцы без товаров, пользователи без заказов. После соединения такие строки находятся по условию `WHERE правая_таблица.id IS NULL`.

### 2.2. Агрегатные функции и группировка

Агрегатные функции вычисляют одно сводное значение по множеству строк:

| Функция | Назначение |
|---|---|
| `COUNT(*)` | количество строк |
| `COUNT(столбец)` | количество строк, где столбец не `NULL` |
| `SUM` | сумма значений |
| `AVG` | среднее значение |
| `MIN`, `MAX` | минимум и максимум |

`GROUP BY` делит строки на группы по значениям перечисленных столбцов. В списке выборки при группировке допустимы только столбцы из `GROUP BY` и агрегатные функции. `HAVING` фильтрует уже сгруппированные данные, тогда как `WHERE` — исходные строки до группировки:

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
```

Пример: количество товаров и средняя цена по категориям:

```sql
SELECT c.name, COUNT(p.id) AS products_count, AVG(p.price) AS avg_price
FROM categories AS c
LEFT JOIN products AS p ON p.category_id = c.id
GROUP BY c.id, c.name;
```

### 2.3. Подзапросы

**Подзапрос** — запрос, вложенный в другой запрос. Он может находиться в `SELECT`, `WHERE`, `FROM` или `HAVING`.

| Вид | Особенность | Пример |
|---|---|---|
| Скалярный | возвращает ровно одно значение | `WHERE price > (SELECT AVG(price) FROM products)` |
| С `IN` | проверяет принадлежность множеству строк | `WHERE seller_id IN (SELECT seller_id FROM products WHERE category_id = 2)` |
| С `EXISTS` | истинен, если подзапрос вернул хотя бы одну строку | `WHERE EXISTS (SELECT 1 FROM reviews r WHERE r.product_id = p.id)` |
| В `FROM` | производная таблица — временный источник строк | `FROM (SELECT ...) AS t` |

**Некоррелированный** подзапрос не зависит от внешнего запроса и вычисляется один раз. **Коррелированный** ссылается на столбцы внешнего запроса и логически вычисляется для каждой его строки — он мощнее, но потенциально дороже.

`EXISTS` удобен для проверки существования связанных данных, `NOT EXISTS` — для поиска строк без связей. В отличие от `IN`, `EXISTS` не даёт неожиданного результата при наличии `NULL` в подзапросе.

### 2.4. Общие табличные выражения (CTE)

CTE, вводимое словом `WITH`, именует промежуточный результат и позволяет обращаться к нему как к таблице в основном запросе. CTE разбивает сложный запрос на логические шаги и делает его читаемым. В одном запросе можно объявить несколько CTE.

**Рекурсивный CTE** (`WITH RECURSIVE`) ссылается сам на себя и применяется для обхода иерархий. Он состоит из:

1. **якорной части** — начальные строки (например, корневые категории);
2. **рекурсивной части** — соединение таблицы с уже полученным результатом;
3. `UNION ALL` между ними.

```sql
WITH RECURSIVE category_tree AS (
    SELECT id, parent_id, name, 0 AS depth
    FROM categories WHERE parent_id IS NULL
    UNION ALL
    SELECT c.id, c.parent_id, c.name, t.depth + 1
    FROM categories AS c
    JOIN category_tree AS t ON t.id = c.parent_id
)
SELECT * FROM category_tree;
```

### 2.5. Представления (`VIEW`)

**Представление** — сохранённый в базе запрос, к которому можно обращаться как к таблице:

```sql
CREATE VIEW v_seller_revenue AS
SELECT s.id, s.store_name, SUM(oi.quantity * oi.unit_price) AS revenue
FROM sellers AS s
JOIN products AS p    ON p.seller_id = s.id
JOIN order_items AS oi ON oi.product_id = p.id
GROUP BY s.id, s.store_name;
```

Обычное представление **не хранит данные** — при каждом обращении выполняется лежащий в основе `SELECT`, поэтому данные всегда актуальны. Представления скрывают сложность запросов, дают готовые аналитические витрины и могут ограничивать доступ к отдельным столбцам.

**Материализованное представление** (`MATERIALIZED VIEW`) физически хранит результат запроса. Оно ускоряет повторное чтение дорогих агрегатов, но данные устаревают между обновлениями; для актуализации используется `REFRESH MATERIALIZED VIEW`.

## 5. Многотабличные и аналитические запросы

Полный текст запросов — в файле [`lab_3queries.sql`](./lab_3queries.sql). Скрипт можно запускать повторно: перед созданием представлений выполняется `DROP VIEW IF EXISTS`.

### 5.1. Запрос 1. `INNER JOIN` трёх таблиц

**Назначение:** показать товары вместе с названием категории и магазином продавца. Соединяются три таблицы: `products`, `categories`, `sellers`.

```sql
SELECT p.id,
       p.title,
       c.name       AS category,
       s.store_name AS seller,
       p.price
FROM products AS p
JOIN categories AS c ON c.id = p.category_id
JOIN sellers    AS s ON s.id = p.seller_id
WHERE p.is_active = TRUE
ORDER BY p.price DESC
LIMIT 15;
```

**Результат (фрагмент):**

| id | title | category | seller | price |
|---:|---|---|---|---:|
| 854 | Книга №854 | Книги | Магазин №9 | 9998.00 |
| 197 | Книга №197 | Книги | Магазин №30 | 9989.00 |
| 1051 | Женское платье №1051 | Женская одежда | Магазин №8 | 9987.00 |
| 394 | Женское платье №394 | Женская одежда | Магазин №29 | 9978.00 |
| 591 | Мужская куртка №591 | Мужская одежда | Магазин №28 | 9967.00 |
| 788 | Пылесос №788 | Пылесосы | Магазин №27 | 9956.00 |

**Пояснение:** `INNER JOIN` оставляет только товары, у которых существуют и категория, и продавец. В схеме оба внешних ключа обязательны (`NOT NULL`), поэтому все 1200 товаров имеют соответствия; соединение нужно для получения текстовых названий вместо идентификаторов.

### 5.2. Запрос 2. `LEFT JOIN`: товары без отзывов

**Назначение:** найти товары, на которые ещё не оставлено ни одного отзыва. Это типичный «анти-join»: левое соединение + проверка `IS NULL` по правой таблице.

```sql
SELECT p.id,
       p.title,
       p.price
FROM products AS p
LEFT JOIN reviews AS r ON r.product_id = p.id
WHERE r.id IS NULL
ORDER BY p.price DESC
LIMIT 15;
```

**Результат (фрагмент):**

| id | title | price |
|---:|---|---:|
| 854 | Книга №854 | 9998.00 |
| 394 | Женское платье №394 | 9978.00 |
| 985 | Блендер №985 | 9945.00 |
| 525 | Наушники №525 | 9925.00 |
| 65 | Ноутбук №65 | 9905.00 |
| 919 | Смартфон №919 | 9903.00 |
| 459 | Спортивный товар №459 | 9883.00 |
| 1050 | Мужская куртка №1050 | 9850.00 |

**Пояснение:** всего в базе **480 товаров без отзывов**. Для товаров с отзывами `LEFT JOIN` даёт строки с заполненным `r.id`, а для товаров без отзывов — одну строку с `NULL`; условие `r.id IS NULL` оставляет только вторые. Если бы использовался `INNER JOIN`, товары без отзывов просто исчезли бы из результата.

### 5.3. Запрос 3. `GROUP BY`: количество товаров и средняя цена по категориям

**Назначение:** построить сводку по категориям: сколько в каждой товаров и какова средняя цена.

```sql
SELECT c.id,
       c.name AS category,
       COUNT(p.id) AS products_count,
       ROUND(AVG(p.price), 2) AS avg_price
FROM categories AS c
LEFT JOIN products AS p ON p.category_id = c.id
GROUP BY c.id, c.name
ORDER BY products_count DESC, c.name;
```

**Результат:**

| id | category | products_count | avg_price |
|---:|---|---:|---:|
| 4 | Аудиотехника | 134 | 5427.89 |
| 3 | Ноутбуки | 134 | 5425.22 |
| 2 | Смартфоны | 134 | 5422.54 |
| 10 | Женская одежда | 133 | 5517.45 |
| 11 | Книги | 133 | 5519.11 |
| 6 | Кухонная техника | 133 | 5444.80 |
| 9 | Мужская одежда | 133 | 5448.12 |
| 7 | Пылесосы | 133 | 5446.46 |
| 12 | Спорт и отдых | 133 | 5453.11 |
| 5 | Бытовая техника | 0 | NULL |
| 8 | Одежда | 0 | NULL |
| 1 | Электроника | 0 | NULL |

**Пояснение:** используется `LEFT JOIN`, поэтому в отчёт попадают и корневые категории, у которых нет товаров напрямую (товары привязаны к листовым подкатегориям). Для них `COUNT(p.id)` равен 0, а `AVG(p.price)` — `NULL`, потому что агрегатные функции игнорируют `NULL`. Если бы использовался `COUNT(*)`, для пустых категорий получилось бы 1 — по одной строке соединения с `NULL`.

### 5.4. Запрос 4. `HAVING`: продавцы с выручкой выше порога

**Назначение:** оставить только продавцов, чья выручка по неотменённым заказам превышает 2 000 000 рублей, и отсортировать их по убыванию выручки.

```sql
SELECT s.id,
       s.store_name,
       COUNT(DISTINCT o.id) AS orders_count,
       SUM(oi.quantity * oi.unit_price) AS revenue
FROM sellers AS s
JOIN products AS p     ON p.seller_id = s.id
JOIN order_items AS oi ON oi.product_id = p.id
JOIN orders AS o       ON o.id = oi.order_id
WHERE o.status <> 'cancelled'
GROUP BY s.id, s.store_name
HAVING SUM(oi.quantity * oi.unit_price) > 2000000
ORDER BY revenue DESC;
```

**Результат (фрагмент):**

| id | store_name | orders_count | revenue |
|---:|---|---:|---:|
| 29 | Магазин №29 | 100 | 2621850.00 |
| 18 | Магазин №18 | 100 | 2565600.00 |
| 24 | Магазин №24 | 100 | 2560500.00 |
| 8 | Магазин №8 | 100 | 2526900.00 |
| 22 | Магазин №22 | 150 | 2525700.00 |
| 19 | Магазин №19 | 100 | 2521950.00 |
| 17 | Магазин №17 | 150 | 2496150.00 |
| 14 | Магазин №14 | 100 | 2481000.00 |

**Пояснение:** порог применяется к **агрегату** `SUM(...)`, поэтому используется `HAVING`, а не `WHERE`. Условие `WHERE o.status <> 'cancelled'` фильтрует исходные строки до группировки. `COUNT(DISTINCT o.id)` нужен потому, что после соединения с позициями один заказ встречается несколько раз. Порог превысили **24 продавца из 30**.

### 5.5. Подзапросы

#### 5.5a. Скалярный подзапрос

**Назначение:** вывести товары дороже средней цены по всему каталогу и показать саму среднюю цену.

```sql
SELECT p.id,
       p.title,
       p.price,
       (SELECT ROUND(AVG(price), 2) FROM products) AS avg_price
FROM products AS p
WHERE p.price > (SELECT AVG(price) FROM products)
ORDER BY p.price DESC
LIMIT 15;
```

**Результат (фрагмент):**

| id | title | price | avg_price |
|---:|---|---:|---:|
| 854 | Книга №854 | 9998.00 | 5456.00 |
| 197 | Книга №197 | 9989.00 | 5456.00 |
| 1051 | Женское платье №1051 | 9987.00 | 5456.00 |
| 394 | Женское платье №394 | 9978.00 | 5456.00 |
| 591 | Мужская куртка №591 | 9967.00 | 5456.00 |
| 788 | Пылесос №788 | 9956.00 | 5456.00 |

**Пояснение:** подзапрос `(SELECT AVG(price) FROM products)` возвращает одно значение — среднюю цену 5456.00. Он некоррелированный: не зависит от внешнего запроса и может быть вычислен один раз. Тот же подзапрос используется и в списке выборки, чтобы показать порог сравнения.

#### 5.5b. Подзапрос с `IN`

**Назначение:** найти продавцов, у которых есть хотя бы один товар в категории «Смартфоны» (`category_id = 2`).

```sql
SELECT s.id,
       s.store_name
FROM sellers AS s
WHERE s.id IN (SELECT p.seller_id
               FROM products AS p
               WHERE p.category_id = 2)
ORDER BY s.id
LIMIT 15;
```

**Результат:**

| id | store_name |
|---:|---|
| 2 | Магазин №2 |
| 5 | Магазин №5 |
| 8 | Магазин №8 |
| 11 | Магазин №11 |
| 14 | Магазин №14 |
| 17 | Магазин №17 |
| 20 | Магазин №20 |
| 23 | Магазин №23 |
| 26 | Магазин №26 |
| 29 | Магазин №29 |

**Пояснение:** внутренний запрос возвращает множество идентификаторов продавцов, у которых есть товары в категории 2; `IN` проверяет принадлежность этому множеству. Подзапрос некоррелированный и выполняется один раз. Обратите внимание: `IN` сам по себе не убирает дубликаты, но здесь `s.id` уникален, поэтому результат не содержит повторов.

#### 5.5c. Подзапрос с `EXISTS`

**Назначение:** найти активные товары, у которых есть хотя бы один отзыв с оценкой 5.

```sql
SELECT p.id,
       p.title,
       p.price
FROM products AS p
WHERE p.is_active = TRUE
  AND EXISTS (SELECT 1
              FROM reviews AS r
              WHERE r.product_id = p.id
                AND r.score = 5)
ORDER BY p.price DESC
LIMIT 15;
```

**Результат (фрагмент):**

| id | title | price |
|---:|---|---:|
| 1051 | Женское платье №1051 | 9987.00 |
| 591 | Мужская куртка №591 | 9967.00 |
| 131 | Пылесос №131 | 9947.00 |
| 1116 | Спортивный товар №1116 | 9892.00 |
| 656 | Книга №656 | 9872.00 |
| 196 | Женское платье №196 | 9852.00 |

**Пояснение:** это **коррелированный** подзапрос: он ссылается на `p.id` из внешнего запроса и логически выполняется для каждого товара. `EXISTS` истинен, как только находится хотя бы один подходящий отзыв, поэтому СУБД может остановить поиск досрочно. Всего таких товаров **240**. Альтернатива через `JOIN` потребовала бы `DISTINCT`, иначе товар повторился бы по числу пятизвёздочных отзывов.

### 5.6. Общие табличные выражения (CTE)

#### 5.6a. CTE: дневная выручка

**Назначение:** разбить расчёт на два шага: сначала выручка по каждому заказу, затем агрегация по дням. Дополнительно вычисляется средняя выручка на заказ.

```sql
WITH order_revenue AS (
    SELECT o.id,
           o.created_at::date AS day,
           SUM(oi.quantity * oi.unit_price) AS revenue
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.id
    WHERE o.status <> 'cancelled'
    GROUP BY o.id, o.created_at
),
daily AS (
    SELECT day,
           SUM(revenue) AS revenue,
           COUNT(*)     AS orders_count
    FROM order_revenue
    GROUP BY day
)
SELECT day,
       revenue,
       orders_count,
       ROUND(revenue / NULLIF(orders_count, 0), 2) AS avg_order_revenue
FROM daily
ORDER BY day DESC
LIMIT 15;
```

#### 5.6b. Рекурсивный CTE: дерево категорий

**Назначение:** обойти иерархию категорий от корней к подкатегориям и показать уровень вложенности и путь.

```sql
WITH RECURSIVE category_tree AS (
    SELECT id,
           parent_id,
           name,
           0 AS depth,
           name::text AS path
    FROM categories
    WHERE parent_id IS NULL
    UNION ALL
    SELECT c.id,
           c.parent_id,
           c.name,
           ct.depth + 1,
           ct.path || ' → ' || c.name
    FROM categories AS c
    JOIN category_tree AS ct ON ct.id = c.parent_id
)
SELECT id,
       depth,
       repeat('  ', depth) || name AS tree_node,
       path
FROM category_tree
ORDER BY path;
```

## 7. Ответы на контрольные вопросы

### 1. Что такое соединение таблиц и по какому условию оно обычно выполняется?

Соединение (`JOIN`) объединяет строки двух таблиц в одну результирующую строку по условию из `ON`. Обычно условие имеет вид `внешний_ключ = первичный_ключ`, например `products.category_id = categories.id`. Без условия соединения (`CROSS JOIN`) получается декартово произведение.

### 2. Чем `INNER JOIN` отличается от `LEFT JOIN`? Приведите пример, где нужен именно `LEFT JOIN`.

`INNER JOIN` возвращает только совпавшие пары строк; строки без пары отбрасываются. `LEFT JOIN` сохраняет все строки левой таблицы, а при отсутствии пары подставляет `NULL` в столбцы правой. `LEFT JOIN` нужен, например, чтобы показать **всех продавцов, включая тех, у кого ещё нет товаров**, или все товары, включая те, у которых нет отзывов. В работе это запрос 2: `products LEFT JOIN reviews ... WHERE r.id IS NULL`.

### 3. Какие агрегатные функции вы знаете? В чём различие между `COUNT(*)` и `COUNT(столбец)`?

`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`. `COUNT(*)` считает все строки группы, а `COUNT(столбец)` — только строки, где значение столбца не `NULL`. Остальные агрегатные функции также игнорируют `NULL`. В запросе 3 `COUNT(p.id)` для пустых категорий даёт 0, а `COUNT(*)` дал бы 1 из-за строки соединения с `NULL`.

### 4. Для чего предназначена секция `GROUP BY` и что допустимо в списке выборки при группировке?

`GROUP BY` делит строки на группы по значениям указанных столбцов; для каждой группы агрегатная функция возвращает одно значение. В списке выборки допустимы столбцы из `GROUP BY`, агрегатные функции и выражения над ними. Нельзя выбирать неключевые столбцы, не входящие в группировку, — их значение в группе неоднозначно. PostgreSQL дополнительно разрешает столбцы, функционально зависящие от первичного ключа группы.

### 5. В чём различие между `WHERE` и `HAVING` и в каком порядке они выполняются?

`WHERE` фильтрует исходные строки **до** группировки и не может использовать агрегатные функции. `HAVING` фильтрует уже сгруппированные данные **после** `GROUP BY` и обычно использует агрегаты. Порядок: `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY`. В работе `WHERE o.status <> 'cancelled'` отбрасывает отменённые заказы, а `HAVING SUM(...) > 2000000` — продавцов с недостаточной выручкой.

### 6. Что такое подзапрос? Чем коррелированный подзапрос отличается от некоррелированного?

Подзапрос — запрос, вложенный в другой запрос. Некоррелированный не зависит от внешнего запроса и может быть вычислен один раз (например, `SELECT AVG(price) FROM products`). Коррелированный ссылается на столбцы внешнего запроса и логически вычисляется для каждой его строки (например, `EXISTS (SELECT 1 FROM reviews r WHERE r.product_id = p.id)`). Коррелированный мощнее, но может быть дороже.

### 7. Как работает предикат `EXISTS` и когда его удобно применять?

`EXISTS (подзапрос)` возвращает `TRUE`, если подзапрос вернул хотя бы одну строку, и `FALSE` в противном случае. СУБД может остановить выполнение на первой найденной строке, поэтому `EXISTS` эффективен для проверки существования связи. Его удобно применять, когда нужно проверить наличие связанных записей без дублирования результата: товары с отзывами, пользователи с заказами, продавцы с товарами. `NOT EXISTS` используется для поиска строк без связей.

### 8. Что такое общее табличное выражение (CTE) и для чего нужен рекурсивный CTE?

CTE (`WITH имя AS (запрос)`) — именованный промежуточный результат, к которому можно обращаться в основном запросе как к таблице. CTE разбивает сложный запрос на читаемые шаги и может использоваться несколько раз. Рекурсивный CTE (`WITH RECURSIVE`) ссылается сам на себя и применяется для обхода иерархий и графов: дерево категорий, организационная структура, маршруты. Он состоит из якорной и рекурсивной частей, соединённых `UNION ALL`.

### 9. Что такое представление (`VIEW`)? Хранит ли обычное представление данные?

Представление — сохранённый в базе именованный запрос, к которому обращаются как к таблице. Обычное представление **не хранит данные**: при каждом обращении выполняется его `SELECT`, поэтому результат всегда актуален. Представления упрощают доступ к сложным запросам, скрывают структуру таблиц и могут ограничивать видимые столбцы.

### 10. Чем материализованное представление отличается от обычного?

Обычное представление — это только сохранённый запрос; данные читаются из базовых таблиц при каждом обращении. Материализованное представление физически хранит результат запроса, поэтому чтение быстрее, но данные могут устаревать. Для обновления используется `REFRESH MATERIALIZED VIEW`; по нему можно строить индексы. Выбор зависит от соотношения «частота чтения / допустимая задержка актуальности».
