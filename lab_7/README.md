## 3. Предметная область и архитектура

Маркетплейс объединяет покупателей, продавцов, товары, заказы, оплату, доставку и отзывы.

![ER-диаграмма](../erd_lab1.png)

**Основные сущности:**

| Сущность | Роль |
|---|---|
| `users` | покупатели, продавцы и администраторы |
| `sellers` | магазины; 1:1 с пользователем-продавцом |
| `categories` | иерархический каталог (самоссылка `parent_id`) |
| `products` | товары продавцов в категориях |
| `stock` | складской остаток; 1:1 с товаром |
| `carts`, `cart_items` | корзина и её позиции (M:N) |
| `orders`, `order_items` | заказ и его позиции (M:N) |
| `payments` | платежи по заказам |
| `reviews` | отзывы покупателей о товарах |
| `addresses` | адреса пользователей |
| `deliveries` | доставка заказа; 1:1 с заказом |
| `product_price_audit` | журнал изменений цен |

**Ключевые связи:**

- пользователь 1:N заказы, отзывы, адреса, корзины;
- продавец 1:N товары;
- категория 1:N товары; категория 1:N подкатегории;
- заказ 1:N позиции; товар 1:N позиции заказов;
- заказ 1:1 доставка; заказ 1:N платежи;
- пользователь + товар → уникальный отзыв.

## 4. Словарь данных

| Таблица | Назначение | Ключевые поля | Ограничения |
|---|---|---|---|
| `users` | пользователи | `id`, `full_name`, `email`, `role` | PK `id`; UNIQUE `email`, `phone`; CHECK `role IN (...)` |
| `categories` | дерево категорий | `id`, `parent_id`, `name` | PK; FK `parent_id → categories.id`; UNIQUE `name` |
| `sellers` | магазины | `id`, `user_id`, `store_name` | PK; FK `user_id → users.id`; UNIQUE `user_id`, `store_name` |
| `products` | товары | `id`, `seller_id`, `category_id`, `price`, `rating`, `attributes` | PK; FK продавец/категория; CHECK `price > 0`, `rating 0..5`, JSONB-объект |
| `stock` | остатки | `product_id`, `quantity` | PK/FK `product_id`; CHECK `quantity >= 0` |
| `carts` | корзины | `id`, `user_id` | PK; FK `user_id → users.id` |
| `cart_items` | позиции корзины | `cart_id`, `product_id`, `quantity` | PK (`cart_id`, `product_id`); FK; CHECK `quantity > 0` |
| `orders` | заказы | `id`, `user_id`, `status`, `total_amount` | PK; FK `user_id`; CHECK `status`, `total_amount >= 0` |
| `order_items` | позиции заказа | `order_id`, `product_id`, `quantity`, `unit_price` | PK (`order_id`, `product_id`); FK; CHECK `quantity > 0`, `unit_price > 0` |
| `payments` | платежи | `id`, `order_id`, `amount`, `status` | PK; FK `order_id`; CHECK `amount > 0`, `status` |
| `reviews` | отзывы | `id`, `user_id`, `product_id`, `score` | PK; FK; CHECK `score 1..5`; UNIQUE (`user_id`, `product_id`) |
| `addresses` | адреса | `id`, `user_id`, `city`, `street`, `house` | PK; FK `user_id` |
| `deliveries` | доставки | `id`, `order_id`, `address_id`, `delivery_status` | PK; FK; UNIQUE `order_id`; CHECK `delivery_status` |
| `product_price_audit` | аудит цен | `id`, `product_id`, `old_price`, `new_price` | PK; FK `product_id` с `ON DELETE CASCADE` |

**Правила удаления:**

- удаление пользователя каскадно удаляет его корзины, отзывы и адреса;
- удаление заказа каскадно удаляет позиции, платежи и доставку;
- удаление товара каскадно удаляет склад, позиции корзин и отзывы, но позиции заказов защищены `ON DELETE RESTRICT`;
- удаление продавца или категории с товарами запрещено (`RESTRICT`), чтобы не потерять историю заказов.

## 5. Нормализация и целостность

### 5.1. Третья нормальная форма

Основная схема приведена к 3НФ:

1. **1НФ:** все столбцы атомарны; повторяющиеся группы вынесены в `order_items`, `cart_items`, `payments`, `addresses`.
2. **2НФ:** в составных ключах (`order_items`, `cart_items`) все неключевые атрибуты зависят от полного ключа.
3. **3НФ:** устранены транзитивные зависимости: название категории хранится только в `categories`, магазин — в `sellers`, цена товара — в `products`, а позиция заказа хранит историческую `unit_price`.

**Осознанные денормализации:**

| Поле | Причина |
|---|---|
| `orders.total_amount` | кэш суммы заказа для быстрых отчётов и проверок; сумма позиций остаётся источником истины |
| `products.rating` | средний рейтинг для каталога; поддерживается триггером при изменении отзывов |
| `products.attributes JSONB` | характеристики, различающиеся по категориям; вынесение в отдельные таблицы усложнило бы схему без пользы для учебного проекта |

Денормализованные поля контролируются: `total_amount` проверяется в итоговых запросах, `rating` пересчитывается триггером, `attributes` ограничен проверкой `jsonb_typeof(...) = 'object'`.

### 5.2. Ограничения целостности

- **PRIMARY KEY** — уникальность и идентификация строк;
- **FOREIGN KEY** — ссылочная целостность; правила `CASCADE`/`RESTRICT`/`SET NULL` выбраны по смыслу связи;
- **UNIQUE** — email, телефон, название магазина, название категории, пара «пользователь + товар» в отзывах;
- **CHECK** — положительная цена, неотрицательный остаток, допустимые статусы, оценка 1–5, рейтинг 0–5;
- **NOT NULL** — обязательные поля;
- **триггеры** — аудит цен и поддержание рейтинга.

| ЛР №7 | [`final_queries.sql`](./final_queries.sql) | итоговый демонстрационный набор: JOIN, агрегация, подзапрос, CTE, окно, JSONB, представление, функция, проверка целостности |

**Пример итогового запроса — топ-3 товара в каждой категории:**

```sql
WITH ranked AS (
    SELECT p.id,
           p.title,
           c.name AS category,
           p.price,
           ROW_NUMBER() OVER (
               PARTITION BY p.category_id
               ORDER BY p.price DESC, p.id
           ) AS rn
    FROM products AS p
    JOIN categories AS c ON c.id = p.category_id
    WHERE p.is_active = TRUE
)
SELECT category, rn, title, price
FROM ranked
WHERE rn <= 3
ORDER BY category, rn;
```

**Пример запроса с долей продавца:**

```sql
WITH seller_category AS (
    SELECT p.category_id,
           p.seller_id,
           SUM(oi.quantity * oi.unit_price) AS revenue
    FROM products AS p
    JOIN order_items AS oi ON oi.product_id = p.id
    JOIN orders AS o      ON o.id = oi.order_id
    WHERE o.status <> 'cancelled'
    GROUP BY p.category_id, p.seller_id
)
SELECT c.name AS category,
       s.store_name AS seller,
       sc.revenue,
       SUM(sc.revenue) OVER (PARTITION BY sc.category_id) AS category_revenue,
       ROUND(sc.revenue
             / SUM(sc.revenue) OVER (PARTITION BY sc.category_id) * 100, 2) AS share_pct
FROM seller_category AS sc
JOIN categories AS c ON c.id = sc.category_id
JOIN sellers    AS s ON s.id = sc.seller_id
ORDER BY category, share_pct DESC;
```

## 10. Серверная логика

Реализована в [`schema_final.sql`](./schema_final.sql) и подробно разобрана в [`../lab_5/README.md`](../lab_5/README.md).

### 10.1. Функция `place_order`

Атомарно создаёт заказ и позицию, проверяет остаток и блокирует складскую строку через `FOR UPDATE`. При нехватке товара возбуждает исключение, поэтому частичный заказ не создаётся.

### 10.2. Функция `seller_revenue`

Возвращает выручку продавца за период с помощью `SELECT ... INTO` и локальной переменной. Для магазина №22 за 2024–2026 годы результат — `2 525 700.00`.

### 10.3. Триггер аудита цены

`trg_products_price_audit` срабатывает после `UPDATE OF price` и записывает `OLD.price`/`NEW.price` в `product_price_audit`. Условие `WHEN (OLD.price IS DISTINCT FROM NEW.price)` исключает ложные срабатывания.

### 10.4. Триггер рейтинга

`trg_refresh_product_rating` срабатывает после вставки, изменения и удаления отзыва и пересчитывает `products.rating` как `AVG(score)`. Это поддерживает денормализованное поле в согласованном состоянии.

## 11. JSONB и современные возможности

В `products` добавлен `attributes JSONB`; для девяти категорий заполнены разные наборы характеристик, каждому товару присвоен `sku`.

Примеры запросов:

```sql
-- Извлечение поля как текста
SELECT title, attributes ->> 'color' AS color
FROM products
WHERE category_id = 2;

-- Проверка вхождения фрагмента
SELECT title, attributes
FROM products
WHERE attributes @> '{"color":"black"}'::jsonb;

-- Проверка наличия ключа
SELECT title, attributes ->> 'author' AS author
FROM products
WHERE category_id = 11 AND attributes ? 'author';
```

GIN-индекс:

```sql
CREATE INDEX idx_products_attributes_gin
    ON products USING GIN (attributes);
```

Он используется для оператора `@>`; на точечном запросе по `sku` план меняется с `Seq Scan` на `Bitmap Index Scan`, время сокращается с `0.330` до `0.042` мс.

## 12. Оптимизация и индексы

Индексы добавлены по результатам `EXPLAIN ANALYZE` (подробности — в [`../lab_6/README.md`](../lab_6/README.md)):

| Запрос | До | После | Индекс |
|---|---|---|---|
| Товары категории 2 с ценой < 3000 | Bitmap Heap Scan + фильтр, 0.122 мс | Index Scan, 0.111 мс | `(category_id, price)` |
| Заказы `paid` за I квартал 2026 | Seq Scan, 0.112 мс | Bitmap Index Scan, 0.094 мс | `(status, created_at)` |
| JSONB `@> '{"sku":"SKU-0854"}'` | Seq Scan, 0.330 мс | Bitmap Index Scan, 0.042 мс | GIN `(attributes)` |
| Вставка 100 000 строк | 55.790 мс без индекса | 229.649 мс с индексом | цена индекса |

**Вывод:** индексы ускоряют чтение, но замедляют запись. Поэтому созданы только индексы под конкретные частые запросы: составной B-tree для каталога, составной B-tree для заказов, GIN для JSONB и индексы по внешним ключам.

## 13. Проверка целостности

Запрос 10 из [`final_queries.sql`](./final_queries.sql) проверяет отсутствие «сирот» и неверных сумм:

| Проверка | Нарушений |
|---|---:|
| Заказы без пользователя | 0 |
| Позиции без заказа | 0 |
| Товары без продавца | 0 |
| Отзывы без товара | 0 |
| Заказы с неверной суммой | 0 |

Дополнительно:

- `products.rating` находится в диапазоне 0–5;
- `stock.quantity >= 0`;
- статусы заказов, платежей и доставок соответствуют `CHECK`;
- уникальные ограничения не позволяют дублировать email, магазины, категории и отзывы одного пользователя на один товар.

## 14. Проектные решения

| Решение | Обоснование |
|---|---|
| PostgreSQL | надёжные транзакции, MVCC, богатые типы (`JSONB`, массивы), оконные функции, PL/pgSQL, GIN |
| Нормализация до 3НФ | устраняет дублирование и аномалии обновления; связи выражены внешними ключами |
| Денормализация `rating` и `total_amount` | ускоряет каталог и отчёты; значения контролируются триггером и проверками |
| JSONB только для характеристик | набор полей различается по категориям; фиксированные столбцы были бы разрежены и неудобны |
| Обычные VIEW, а не материализованные | данные малы, нужна актуальность; MATERIALIZED VIEW добавил бы необходимость REFRESH |
| Триггеры для аудита и рейтинга | правила должны применяться независимо от приложения и не могут быть обойдены |
| Функция `place_order` в БД | заказ, позиции и остаток должны меняться атомарно; нужна блокировка строки склада |
| Индексы по планам | каждый индекс обоснован конкретным запросом; лишние индексы замедляют запись |

## 15. Возможные вопросы на защите

**Почему схема считается нормализованной, если есть `total_amount` и `rating`?**  
Основная схема находится в 3НФ; это осознанные денормализованные кэши. `rating` поддерживается триггером, `total_amount` проверяется по сумме позиций. Они нужны для производительности и удобства отчётов, а не заменяют нормализованные данные.

**Почему характеристики товаров хранятся в JSONB, а не в отдельной таблице?**  
Набор атрибутов различается по категориям: у смартфона — диагональ и память, у книги — автор и страницы. JSONB позволяет хранить разные наборы без разреженных столбцов и сложных связей. Для часто используемых полей (цена, категория, продавец) оставлены обычные столбцы.

**Почему для JSONB нужен именно GIN?**  
B-tree не поддерживает containment `@>` для составных значений. GIN строит инвертированный индекс по ключам и значениям и позволяет быстро находить документы, содержащие фрагмент.

**Зачем `FOR UPDATE` в `place_order`?**  
Он блокирует складскую строку до конца транзакции, чтобы два параллельных заказа не прочитали один остаток и не продали его дважды.

**Почему аудит цены — триггер, а не код приложения?**  
Цена может меняться из разных приложений и скриптов; триггер гарантирует запись в журнал независимо от источника изменения.

**Как воспроизвести проект?**  
Создать базу, выполнить `lab_7/schema_final.sql`, затем `lab_2/lab_2seed.sql`, `lab_3/lab_3queries.sql`, `lab_6/lab_6json_indexes.sql` и `lab_7/final_queries.sql`. Порядок описан в приложении.
