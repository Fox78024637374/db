## 2. Теоретическая база

### 2.1. Транзакции и ACID

**Транзакция** — последовательность операций, выполняемая как единое неделимое целое: либо применяются все её изменения, либо ни одно.

| Свойство | Смысл |
|---|---|
| **Atomicity** (атомарность) | «всё или ничего»: при сбое на любом шаге изменения откатываются |
| **Consistency** (согласованность) | транзакция переводит базу из одного корректного состояния в другое, не нарушая ограничений |
| **Isolation** (изоляция) | параллельные транзакции не мешают друг другу; совместный эффект эквивалентен некоторому последовательному выполнению |
| **Durability** (долговечность) | зафиксированные изменения сохраняются после сбоя |

Транзакция начинается командой `BEGIN` и завершается:

- `COMMIT` — фиксирует изменения, делает их видимыми и постоянными;
- `ROLLBACK` — отменяет изменения и возвращает базу к состоянию до начала транзакции.

`SAVEPOINT` создаёт внутри транзакции точку, к которой можно частично откатиться командой `ROLLBACK TO SAVEPOINT`. Вне явного `BEGIN` каждая команда выполняется в собственной транзакции (автокоммит).

### 2.2. Изоляция и MVCC

PostgreSQL поддерживает уровни изоляции:

| Уровень | Особенность |
|---|---|
| `READ COMMITTED` | по умолчанию; каждая команда видит снимок, зафиксированный до её начала |
| `REPEATABLE READ` | транзакция видит единый снимок данных |
| `SERIALIZABLE` | эмулирует последовательное выполнение транзакций |

Изоляция реализована через **MVCC** (многоверсионное управление конкурентным доступом): читающие транзакции видят согласованный снимок и не блокируют пишущие. Это важно для маркетплейса, где одновременно оформляются заказы, меняются остатки и читаются отчёты.

### 2.3. Функции PL/pgSQL

PL/pgSQL — процедурный язык PostgreSQL. Тело функции заключается между `BEGIN` и `END`, локальные переменные объявляются в `DECLARE`. Поддерживаются:

- присваивание и `SELECT ... INTO`;
- ветвление `IF ... THEN ... ELSE`;
- циклы `LOOP`, `WHILE`, `FOR`;
- `RETURN` для возврата значения;
- `RAISE EXCEPTION` для прерывания выполнения;
- блок `EXCEPTION` для перехвата ошибок.

Функция оформления заказа должна быть **атомарной**: создать заказ, позиции и уменьшить остаток, а при нехватке товара — возбудить исключение, не оставив частичных изменений.

### 2.4. Триггеры

**Триггер** автоматически вызывает триггерную функцию при изменении данных.

| Признак | Варианты |
|---|---|
| Событие | `INSERT`, `UPDATE`, `DELETE` |
| Момент | `BEFORE`, `AFTER`, `INSTEAD OF` |
| Уровень | `FOR EACH ROW`, `FOR EACH STATEMENT` |
| Псевдозаписи | `NEW` (новая строка), `OLD` (прежняя строка) |

`BEFORE` удобен для проверки или корректировки данных до записи, `AFTER` — для аудита и пересчёта связанных данных. Триггеры применяют для журналирования, валидации, автоматического заполнения вычисляемых полей и поддержания денормализованных значений.

CREATE TABLE product_price_audit (

    new_price   NUMERIC(12,2),

## 5. Транзакции: COMMIT, ROLLBACK, SAVEPOINT

### 5.1. Транзакция с COMMIT

Сценарий создаёт заказ, позицию заказа и уменьшает остаток товара. Идентификатор заказа сохраняется во временную таблицу, чтобы затем показать результат и корректно очистить данные.

```sql
BEGIN;
WITH new_order AS (
    INSERT INTO orders (user_id, status, total_amount)
    VALUES (1, 'created', (SELECT price FROM products WHERE id = 1) * 2)
    RETURNING id
)
INSERT INTO lab5_tx_demo (order_id, product_id, qty)
SELECT id, 1, 2 FROM new_order;

INSERT INTO order_items (order_id, product_id, quantity, unit_price)
SELECT d.order_id, d.product_id, d.qty, p.price
FROM lab5_tx_demo AS d
JOIN products AS p ON p.id = d.product_id;

UPDATE stock AS s
SET quantity = s.quantity - d.qty,
    updated_at = now()
FROM lab5_tx_demo AS d
WHERE s.product_id = d.product_id;
COMMIT;
```

**Результат:**

| order_id | status | total_amount | product_id | quantity | unit_price | stock_after |
|---:|---|---:|---:|---:|---:|---:|
| 1501 | created | 2274.00 | 1 | 2 | 1137.00 | 35 |

Заказ, позиция и остаток изменились согласованно. После демонстрации скрипт возвращает остаток и удаляет тестовый заказ, чтобы не засорять базу.

### 5.2. Транзакция с ROLLBACK

Повторяем сценарий, но вместо `COMMIT` выполняем `ROLLBACK` (имитация сбоя после изменений).

```sql
SELECT count(*) AS orders_before,
       (SELECT quantity FROM stock WHERE product_id = 1) AS stock_before
FROM orders;

BEGIN;
-- INSERT заказа, INSERT позиции, UPDATE остатка
ROLLBACK;

SELECT count(*) AS orders_after,
       (SELECT quantity FROM stock WHERE product_id = 1) AS stock_after
FROM orders;
```

**Результат:**

| orders_before | stock_before |
|---:|---:|
| 1500 | 37 |

| orders_after | stock_after |
|---:|---:|
| 1500 | 37 |

Количество заказов и остаток не изменились: `ROLLBACK` отменил все операции транзакции.

### 5.3. SAVEPOINT

`SAVEPOINT` позволяет откатить часть транзакции, сохранив изменения до точки.

```sql
BEGIN;
UPDATE stock SET quantity = quantity - 1 WHERE product_id = 1;
SAVEPOINT sp_stock;
UPDATE stock SET quantity = quantity - 10 WHERE product_id = 1;
ROLLBACK TO SAVEPOINT sp_stock;
COMMIT;
```

**Результат:** остаток стал `36` (откатилось только второе изменение на 10), после чего скрипт восстанавливает исходное значение `37`. Это показывает разницу между полным `ROLLBACK` и частичным `ROLLBACK TO SAVEPOINT`.

## 6. Функция оформления заказа

Функция `place_order` принимает пользователя, товар и количество. Она:

1. проверяет положительность количества и существование пользователя;
2. читает цену активного товара;
3. блокирует складскую строку через `FOR UPDATE`, чтобы параллельные заказы не продали один и тот же остаток;
4. проверяет достаточность остатка;
5. создаёт заказ и позицию;
6. уменьшает остаток;
7. возвращает идентификатор заказа.

```sql
CREATE OR REPLACE FUNCTION place_order(
    p_user    BIGINT,
    p_product BIGINT,
    p_qty     INT
)
RETURNS BIGINT
LANGUAGE plpgsql
AS $$
DECLARE
    v_order_id BIGINT;
    v_price    NUMERIC(12,2);
    v_stock    INT;
BEGIN
    IF p_qty IS NULL OR p_qty <= 0 THEN
        RAISE EXCEPTION 'Количество должно быть положительным (передано %)', p_qty;
    END IF;

    IF NOT EXISTS (SELECT 1 FROM users WHERE id = p_user) THEN
        RAISE EXCEPTION 'Пользователь % не найден', p_user;
    END IF;

    SELECT price INTO v_price
    FROM products
    WHERE id = p_product AND is_active = TRUE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Товар % не найден или неактивен', p_product;
    END IF;

    SELECT quantity INTO v_stock
    FROM stock
    WHERE product_id = p_product
    FOR UPDATE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Для товара % нет складской записи', p_product;
    END IF;

    IF v_stock < p_qty THEN
        RAISE EXCEPTION 'Недостаточно товара на складе (id=%, остаток=%, запрошено=%)',
            p_product, v_stock, p_qty;
    END IF;

    INSERT INTO orders (user_id, status, total_amount)
    VALUES (p_user, 'created', v_price * p_qty)
    RETURNING id INTO v_order_id;

    INSERT INTO order_items (order_id, product_id, quantity, unit_price)
    VALUES (v_order_id, p_product, p_qty, v_price);

    UPDATE stock
    SET quantity = quantity - p_qty,
        updated_at = now()
    WHERE product_id = p_product;

    RETURN v_order_id;
END;
$$;
```

### 6.1. Успешный вызов

```sql
BEGIN;
SELECT place_order(1, 1, 2) AS new_order_id;
SELECT o.id, o.total_amount, oi.product_id, oi.quantity, oi.unit_price, s.quantity AS stock_after
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id
JOIN stock AS s       ON s.product_id = oi.product_id
WHERE o.id = (SELECT max(id) FROM orders);
ROLLBACK;
```

**Результат:**

| new_order_id |
|---:|
| 1503 |

| order_id | total_amount | product_id | quantity | unit_price | stock_after |
|---:|---:|---:|---:|---:|---:|
| 1503 | 2274.00 | 1 | 2 | 1137.00 | 35 |

Транзакция откатана, поэтому тестовый заказ в базе не остался.

### 6.2. Ошибка при нехватке товара

Вызов с количеством `999999` при остатке `37`:

```sql
DO $$
BEGIN
    PERFORM place_order(1, 1, 999999);
EXCEPTION WHEN OTHERS THEN
    RAISE NOTICE 'Ожидаемая ошибка: %', SQLERRM;
END;
$$;
```

**Сообщения:**

```text
Ожидаемая ошибка: Недостаточно товара на складе (id=1, остаток=37, запрошено=999999)
Остаток до=37, после=37
Заказов до=1500, после=1500
```

Исключение прервало функцию до вставки заказа; остаток и количество заказов не изменились. Это и есть атомарность: частичного заказа не возникает.

> В реальной нагрузке `FOR UPDATE` блокирует строку склада до конца транзакции, поэтому два параллельных заказа не смогут одновременно списать один и тот же остаток.

## 7. Функция расчёта выручки продавца

Функция использует локальную переменную и `SELECT ... INTO`:

```sql
CREATE OR REPLACE FUNCTION seller_revenue(
    p_seller_id BIGINT,
    p_from      DATE,
    p_to        DATE
)
RETURNS NUMERIC
LANGUAGE plpgsql
AS $$
DECLARE
    v_revenue NUMERIC(14,2);
BEGIN
    SELECT COALESCE(SUM(oi.quantity * oi.unit_price), 0)
    INTO v_revenue
    FROM sellers AS s
    JOIN products AS p     ON p.seller_id = s.id
    JOIN order_items AS oi ON oi.product_id = p.id
    JOIN orders AS o       ON o.id = oi.order_id
    WHERE s.id = p_seller_id
      AND o.status <> 'cancelled'
      AND o.created_at::date BETWEEN p_from AND p_to;

    RETURN v_revenue;
END;
$$;
```

**Проверка:**

```sql
SELECT seller_revenue(22, DATE '2024-01-01', DATE '2026-12-31');
```

| seller_22_revenue |
|---:|
| 2525700.00 |

Значение совпадает с выручкой магазина №22 в лабораторной работе №4, где она рассчитывалась оконными функциями. Это подтверждает корректность функции.

## 8. Триггер аудита изменения цены

Триггер срабатывает **после** обновления цены и записывает старое и новое значение. Условие `WHEN (OLD.price IS DISTINCT FROM NEW.price)` не создаёт запись, если цена фактически не изменилась.

```sql
CREATE OR REPLACE FUNCTION log_product_price_change()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO product_price_audit (product_id, old_price, new_price)
    VALUES (OLD.id, OLD.price, NEW.price);
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_products_price_audit
AFTER UPDATE OF price ON products
FOR EACH ROW
WHEN (OLD.price IS DISTINCT FROM NEW.price)
EXECUTE FUNCTION log_product_price_change();
```

**Проверка:** цена товара 854 увеличена на 100, затем возвращена обратно.

```sql
UPDATE products SET price = price + 100 WHERE id = 854;
UPDATE products SET price = price - 100 WHERE id = 854;

SELECT id, product_id, old_price, new_price, changed_at
FROM product_price_audit
WHERE product_id = 854
ORDER BY id DESC
LIMIT 2;
```

**Результат:**

| id | product_id | old_price | new_price | changed_at |
|---:|---:|---:|---:|---|
| 2 | 854 | 10098.00 | 9998.00 | 2026-10-22 23:09:30+03 |
| 1 | 854 | 9998.00 | 10098.00 | 2026-10-22 23:09:30+03 |

Журнал автоматически сохранил обе операции. Цена товара после проверки равна исходным `9998.00`.

## 9. Триггер поддержания рейтинга

В таблицу `products` добавлено денормализованное поле `rating`. Триггер пересчитывает средний рейтинг при вставке, изменении и удалении отзыва.

```sql
CREATE OR REPLACE FUNCTION refresh_product_rating()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
DECLARE
    v_product_id BIGINT;
BEGIN
    IF TG_OP = 'DELETE' THEN
        v_product_id := OLD.product_id;
    ELSE
        v_product_id := NEW.product_id;
    END IF;

    UPDATE products
    SET rating = COALESCE(
            (SELECT ROUND(AVG(score), 2)
             FROM reviews
             WHERE product_id = v_product_id),
            0
        )
    WHERE id = v_product_id;

    RETURN COALESCE(NEW, OLD);
END;
$$;

CREATE TRIGGER trg_refresh_product_rating
AFTER INSERT OR UPDATE OR DELETE ON reviews
FOR EACH ROW
EXECUTE FUNCTION refresh_product_rating();
```

**Проверка:** у товара 854 изначально нет отзывов, рейтинг `0.00`. В транзакции добавляется отзыв с оценкой 5:

```sql
BEGIN;
INSERT INTO reviews (user_id, product_id, score, comment)
VALUES (1, 854, 5, 'Тестовый отзыв для проверки триггера');
SELECT id, rating FROM products WHERE id = 854;
ROLLBACK;
```

**Результат:**

| Этап | rating |
|---|---:|
| до вставки | 0.00 |
| после вставки | 5.00 |
| после ROLLBACK | 0.00 |

Триггер пересчитал средний рейтинг; откат транзакции вернул и отзыв, и рейтинг. При наличии нескольких отзывов используется `AVG(score)`, поэтому значение автоматически становится средним.

## 10. Логика в БД или в приложении

| Логика | Где размещать | Почему |
|---|---|---|
| Ограничения `PK`, `FK`, `UNIQUE`, `CHECK` | БД | гарантируют целостность независимо от приложения |
| Атомарное оформление заказа, списание остатка | БД (функция) | несколько таблиц должны меняться согласованно; нужна блокировка остатка |
| Аудит изменения цены | БД (триггер) | нельзя обойти, даже если цена меняется из другого приложения |
| Средний рейтинг товара | БД (триггер) | денормализованное поле должно всегда соответствовать отзывам |
| Расчёт выручки за период | БД или приложение | в БД удобно для отчётов; в приложении — если нужна сложная бизнес-логика |
| Отображение каталога, корзина, рекомендации | Приложение | не связано с целостностью, часто меняется, требует гибкости |
| Интеграции с внешними сервисами | Приложение | СУБД не должна зависеть от внешних API |

**Достоинства серверной логики:** единые правила для всех клиентов, целостность на уровне хранилища, меньше передачи данных, вычисления рядом с данными.  
**Недостатки:** сложнее тестировать и отлаживать, привязка к конкретной СУБД, дополнительная нагрузка на сервер, нужна дисциплина версионирования.

Поэтому в БД держат логику, неразрывно связанную с целостностью (транзакции, ограничения, аудит, пересчёт связанных полей), а прикладную бизнес-логику — в приложении.

## 12. Ответы на контрольные вопросы

### 1. Что такое транзакция и какими свойствами ACID она обладает?

Транзакция — последовательность операций, выполняемая как единое целое. ACID: атомарность (всё или ничего), согласованность (переход между корректными состояниями), изоляция (параллельные транзакции не мешают друг другу), долговечность (зафиксированные изменения сохраняются после сбоя).

### 2. Что делают команды COMMIT и ROLLBACK? Для чего нужен SAVEPOINT?

`COMMIT` фиксирует изменения транзакции и делает их постоянными. `ROLLBACK` отменяет все изменения транзакции. `SAVEPOINT` создаёт промежуточную точку; `ROLLBACK TO SAVEPOINT` отменяет только часть операций после неё, сохраняя более ранние изменения.

### 3. Приведите пример сценария в маркетплейсе, где необходима транзакция, и объясните почему.

Оформление заказа: нужно одновременно создать запись заказа, добавить позиции и уменьшить остаток на складе. Если товара не хватает или происходит сбой, нельзя оставлять «половину» заказа — иначе данные о заказе и складе будут противоречить друг другу. Транзакция гарантирует, что либо все изменения применятся, либо ни одно.

### 4. Что обеспечивает свойство атомарности и что — свойство изоляции транзакции?

Атомарность гарантирует, что транзакция выполняется целиком или не выполняется вовсе; при ошибке все её изменения откатываются. Изоляция определяет, какие изменения параллельных транзакций видны текущей, и не позволяет им искажать результат друг друга.

### 5. Что такое функция в PostgreSQL и какие конструкции предоставляет язык PL/pgSQL?

Функция — именованный серверный объект, возвращающий значение и выполняющий код в базе. PL/pgSQL предоставляет переменные (`DECLARE`), присваивание, `SELECT ... INTO`, ветвления `IF`, циклы `LOOP`/`WHILE`/`FOR`, `RETURN`, `RAISE EXCEPTION`, блоки `EXCEPTION`.

### 6. Как в функции PL/pgSQL обработать ошибочную ситуацию и прервать выполнение?

Для прерывания используется `RAISE EXCEPTION 'текст'` (можно с параметрами `%`). Для перехвата — блок `BEGIN ... EXCEPTION WHEN OTHERS THEN ... END;`. При исключении изменения текущей транзакции (или подтранзакции блока) откатываются.

### 7. Что такое триггер и в ответ на какие события он срабатывает?

Триггер — объект, автоматически вызывающий функцию при изменении данных. События: `INSERT`, `UPDATE`, `DELETE`; для представлений — `INSTEAD OF`. Триггер задаёт момент (`BEFORE`/`AFTER`) и уровень (`FOR EACH ROW`/`FOR EACH STATEMENT`).

### 8. Чем различаются триггеры BEFORE и AFTER, а также уровня строки и уровня оператора? Что такое NEW и OLD?

`BEFORE` выполняется до изменения строки и может проверить или скорректировать данные; `AFTER` — после изменения, удобен для аудита и пересчёта связанных данных. `FOR EACH ROW` срабатывает на каждую строку, `FOR EACH STATEMENT` — один раз на оператор. `NEW` — новая версия строки, `OLD` — прежняя; в `INSERT` доступен только `NEW`, в `DELETE` — только `OLD`.

### 9. Для каких задач применяют триггеры? Приведите примеры из кейса маркетплейса.

Для аудита изменений (журнал цен), поддержания денормализованных полей (средний рейтинг товара), валидации данных, автоматического заполнения вычисляемых полей, каскадного пересчёта связанных данных. В работе реализованы аудит цены и пересчёт рейтинга.

### 10. Каковы достоинства и недостатки размещения бизнес-логики на стороне СУБД?

Достоинства: единые правила для всех приложений, гарантия целостности, вычисления рядом с данными, меньше сетевого обмена. Недостатки: сложнее тестировать и отлаживать, привязка к СУБД, нагрузка на сервер, необходимость версионирования. Логику целостности держат в БД, прикладную бизнес-логику — в приложении.
